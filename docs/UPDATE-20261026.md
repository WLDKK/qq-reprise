# 打卡计时精度与脱敏诊断维护

此前打卡服务实际每 15 秒检查一次，文档却描述为约每秒。旧用例主要主动调用 `tick`，未覆盖这个真实计时器差异。本次修复独立计时器，并增加虚拟时间回调、界面保存和生产计时验收。

- 新增独立设置 `scheduler_interval_ms`，默认 1000 毫秒，可设 250–60000 毫秒；只影响打卡服务。QQ 连接看护、AI 和其他后台任务的周期保持原状。
- 检查时先用本地时间、时区、计划和持久去重记录判断是否到期。未到点不调用群接口；检查次数不等于网络请求次数。
- 检查精度与任务启动间隔、并发上限、失败退避分别配置。实时改精度会替换原计时器，不叠加多个定时器；旧配置缺少新字段时默认每秒检查，旧客户端遗漏该字段保存时保留现值。
- 保留账号＋群＋日期去重、未知不重打、独立名单、首日跳过和补打窗口。日期确认仍受 UTC 查询日限制。
- 本机界面与健康摘要显示本功能的检查计数、最近检查间隔、元数据/打卡调用计数，不含账号、群号或聊天。调用次数只表示本地尝试，不代表服务端处理或业务成功。

PacketBackend 诊断通过现有认证连接按需获取 `message` / `wording`。仅固定只读状态接口可显式开启这些字段；普通消息接口错误仍只保留分类。正文限制长度并标注截断，隐藏用户目录、账号标识、认证头、Cookie、API 密钥和带凭据/查询参数的 URL。没有记录完整 headers 或其他接口消息正文。

新回归覆盖真实计时回调、修改精度后无重复计时、未到点零调用、跨午夜、旧设置保存与重启、分群时区、诊断专用传输路径及脱敏。首次精度用例有两处虚拟时钟夹具问题：批量推进时多个回调共享最终时间，以及未等待上次异步 tick 收尾；已改为逐秒推进和等待收尾，运行防重逻辑未因此放宽。

本版验证结果见 [测试记录](../TESTING.md)。生产验收只观察非到点窗口中的实际 tick 和只读能力；**未执行真实群打卡，不承诺抢到第一或固定网络耗时**。NapCat / QQ 必须兼容并在线；例如 Windows QQ `9.9.36-53644` 的相关适配从 [NapCat 4.18.34](https://github.com/NapNeko/NapCatQQ/releases/tag/v4.18.34) 开始加入。

本轮还在已配置计划的非到点窗口观察了实际后台计时，间隔约一秒，窗口内元数据及打卡调用均为零；之后才显式刷新只读能力缓存。公开说明只保留验收结论，原始生产样本、账号、配置和日志均不随源码发布。
